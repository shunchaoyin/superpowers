# Test-Driven Development Skill 笔记

> 原始技能：`skills/test-driven-development/SKILL.md`  
> 作用：实现功能、修 Bug 或改行为前，强制使用 RED-GREEN-REFACTOR。

---

## 一、核心定位

`test-driven-development` 是 Superpowers 中最刚性的纪律技能之一。它的核心不是“有测试”，而是“先写测试，并亲眼看到测试因正确原因失败”。

铁律：

```text
NO PRODUCTION CODE WITHOUT A FAILING TEST FIRST
```

如果已经先写了生产代码，技能要求删除它，重新从失败测试开始。

## 二、何时使用

必须使用：

- 新功能
- Bug 修复
- 重构
- 行为变化

例外需要问用户：

- 一次性原型
- 生成代码
- 配置文件

## 三、RED-GREEN-REFACTOR

| 阶段 | 要求 | 通过标准 |
|------|------|----------|
| RED | 写一个最小失败测试 | 失败原因正是功能缺失或 Bug 存在 |
| GREEN | 写最小实现 | 新测试通过，其他测试不坏 |
| REFACTOR | 清理命名、重复和结构 | 测试始终保持绿色 |

最关键的是 RED 阶段的验证：测试如果一开始就通过，说明它没有证明任何东西。

## 四、好测试的特征

- 测一个行为，不把多个行为塞进一个测试
- 名字清楚描述行为
- 尽量测试真实代码，而不是测试 mock 本身
- 展示期望 API 和使用方式
- 失败信息能说明问题

如果测试名里出现多个 `and`，通常应该拆分。

## 五、为什么不能“事后补测试”

事后测试回答的是：

```text
这段代码做了什么？
```

测试先行回答的是：

```text
这段代码应该做什么？
```

事后测试会被既有实现污染，容易只覆盖自己记得的边界；测试先行会迫使你先定义行为，再实现。

## 六、红旗

出现以下想法时，应停止并回到 RED：

- 代码先于测试
- “我稍后补测试”
- 测试第一次运行就通过
- 不知道测试为什么失败
- “太简单了，不用测”
- “我已经手测了”
- “保留已有代码当参考”
- “这次情况特殊”

## 七、与其他技能的关系

| Skill | 关系 |
|-------|------|
| `systematic-debugging` | Phase 4 创建失败测试时调用 TDD |
| `writing-plans` | 计划步骤要按 TDD 拆分 |
| `subagent-driven-development` | 子代理实现任务时应遵循 TDD |
| `verification-before-completion` | TDD 后仍需完成前新鲜验证 |

## 八、一句话记忆

TDD 的证据链是：先证明测试能抓住问题，再写最小代码让它通过。
