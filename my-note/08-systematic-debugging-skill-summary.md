# Systematic Debugging Skill 笔记

> 原始技能：`skills/systematic-debugging/SKILL.md`  
> 作用：遇到 Bug、测试失败、构建失败或异常行为时，先找根因，再修复。

---

## 一、核心定位

`systematic-debugging` 是反“猜修复”的调试流程。它要求先完成根因调查，才能提出修复方案。

铁律：

```text
NO FIXES WITHOUT ROOT CAUSE INVESTIGATION FIRST
```

只修症状、凭直觉试补丁、一次改多个变量，都是这个技能要防止的失败模式。

## 二、何时使用

任何技术异常都要用：

- 测试失败
- 线上或本地 Bug
- 构建失败
- 性能问题
- 集成问题
- 行为与预期不符

越是“看起来很简单”或“赶时间”，越容易猜错，所以越要使用。

## 三、四阶段流程

### Phase 1：根因调查

必须先做：

- 仔细读错误信息和完整 stack trace
- 稳定复现问题
- 检查最近变更
- 多组件系统中在边界加诊断日志
- 追踪坏数据从哪里进入系统

成功标准：知道发生了什么，以及为什么发生。

### Phase 2：模式分析

寻找同代码库里的工作样例，完整阅读参考实现，比较工作代码和坏代码的差异，理解依赖、配置和假设。

成功标准：知道坏路径和好路径的关键差异。

### Phase 3：假设与测试

一次只形成一个明确假设：

```text
我认为 X 是根因，因为 Y。
```

然后做最小实验验证。实验失败时形成新假设，而不是叠加更多补丁。

### Phase 4：实现修复

修根因，而不是修症状：

- 先创建失败测试
- 使用 `test-driven-development`
- 只做一个修复
- 验证新测试和回归测试
- 如果修复失败，回到 Phase 1

如果连续 3 次修复失败，要停止并质疑架构，而不是继续尝试第 4 个补丁。

## 五、红旗

- “先试这个看看”
- “快速修一下，之后再查”
- 同时改多个东西
- 跳过失败测试
- 没理解问题但觉得某个修复可能有效
- 只看了参考实现的一部分
- 已失败两次还想“再试一次”

## 六、与其他技能的关系

|-------|------|
| `test-driven-development` | Phase 4 写失败测试和修复 |
| `verification-before-completion` | 修复后声明完成前必须新鲜验证 |
| `dispatching-parallel-agents` | 多个独立失败域可并发调查 |

## 七、一句话记忆

系统化调试先回答“为什么坏”，再回答“怎么修”；没有根因，就没有修复。
