# Dispatching Parallel Agents Skill 笔记

> 原始技能：`skills/dispatching-parallel-agents/SKILL.md`  
> 作用：当多个问题彼此独立时，并发派发多个子代理分别调查或修复。

---

## 一、核心定位

`dispatching-parallel-agents` 是并发调查技能。它不适合所有多任务场景，只适合问题域互相独立、不会共享状态或互相覆盖的情况。

核心原则：

```text
每个独立问题域派发一个代理，并发工作，最后统一审查和整合。
```

## 二、何时使用

适用场景：

- 3 个以上测试文件失败，且根因看起来不同
- 多个子系统分别出问题
- 每个问题不需要其他问题的上下文
- 子代理之间不会编辑同一批文件或共享运行状态

不适用场景：

- 失败可能互相关联，一个修复可能影响全部
- 需要先理解整个系统状态
- 还处在探索阶段，不知道问题怎么分组
- 子代理会互相干扰

## 三、标准模式

| 步骤 | 内容 |
|------|------|
| 1 | 按问题域分组，例如不同测试文件或子系统 |
| 2 | 为每个代理写聚焦任务 |
| 3 | 并发派发 |
| 4 | 收回结果后审查 summary |
| 5 | 检查冲突并运行完整测试 |

好的子代理任务应包含：

- 明确范围：只处理某个文件或子系统
- 清晰目标：例如让某几个测试通过
- 约束：不要改其他代码，或不要增加 timeout
- 输出要求：总结根因和改动

## 四、好提示词的结构

一个好的并行代理提示词应该回答：

```text
你要修什么？
失败现象是什么？
怀疑方向是什么？
允许改什么，不允许改什么？
返回时要报告什么？
```

重点是缩小上下文。提示越宽泛，代理越容易重构过度或偏离任务。

## 五、常见错误

| 错误 | 后果 | 修正 |
|------|------|------|
| “修所有测试” | 范围过大，代理迷路 | 只给一个问题域 |
| 不提供错误信息 | 代理需要重新探索 | 粘贴测试名和失败信息 |
| 没有限制 | 代理可能大改系统 | 写明可改范围 |
| 输出要求模糊 | 无法整合结果 | 要求根因和改动摘要 |

## 六、验证要求

子代理返回后不能直接信任结果。主代理必须：

- 阅读每个 summary
- 查看是否编辑了相同文件
- 运行完整测试套件
- 抽查关键改动是否符合约束

## 七、与其他技能的区别

| Skill | 区别 |
|-------|------|
| `subagent-driven-development` | 按计划顺序执行任务，不并行实现 |
| `dispatching-parallel-agents` | 并发调查多个独立问题 |
| `systematic-debugging` | 单个问题的根因调查流程 |

## 八、一句话记忆

并行代理不是“多叫几个人快一点”，而是“独立问题域可以同时调查，最后必须统一验证”。
